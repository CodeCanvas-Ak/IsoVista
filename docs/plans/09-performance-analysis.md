# 09 · Performance Analysis

## 1. 目标

性能分析回答两个问题：checker 在同一输入上花费了多少资源，以及结论能否在相同协议下复现。指标定义和比较规则由本文维护，运行文件布局由 10 维护。

不把单个机器上的绝对耗时写成平台固定指标，也不把不同隔离规格、不同历史或不同预算的结果直接排名。

## 2. 指标定义

| 类别 | 指标 | 口径 |
| --- | --- | --- |
| 正确性 | `accept/reject` | 仅来自完成的 checker 结果 |
| 非结论状态 | `timeout/oom/error/skipped` | 单独计数，不计为 accept 或 reject |
| 总体开销 | wall time | 从明确起点到终点的实际耗时，包含哪些阶段须固定 |
| 分阶段开销 | stage time | 使用标准阶段名，单位统一为 ms |
| 内存 | peak RSS 或现有 JVM 指标 | 标明测量对象与采样方式，不混称同一种内存 |
| 运行环境 | CPU、核数、内存、OS、JVM、求解器、DBMS 版本 | 每次实验记录实际值 |
| 输入规模 | 事务数、操作数、键数、图节点/边数 | 从实际历史或图计算，不只看请求参数 |
| 求解器/算法统计 | 调用次数、约束数、剪枝率等 | 仅在工具真实暴露时记录 |

缺失值写 `null`，不能写成 0。采样得到的峰值应注明采样间隔，避免把采样下界当成精确峰值。

## 3. 标准阶段

| 阶段 | 含义 |
| --- | --- |
| `Construction` | 历史读取后的图或内部结构构建 |
| `Encoding` | SAT/SMT 等约束编码 |
| `Pruning` | 约束、图或可达性剪枝 |
| `Solving` | 求解器耗时 |
| `Traversal` | 图遍历和环检测 |
| `IO` | 单独计量的序列化与反例输出 |
| `Untracked` | 总耗时减去已记录阶段后的差额 |

并非每个 checker 都有全部阶段。比较时允许只比较共同阶段，同时保留总耗时；`Untracked` 用于对账，不能隐藏到其他阶段中。

## 4. 公平比较协议

1. **同输入**：共享同一历史文件并校验 SHA-256；确认模型、规格和假设兼容。
2. **同预算**：统一 timeout、内存和可用核数，记录实际限制及是否成功执行。
3. **同环境**：尽量使用同一容器或机器镜像，固定 JVM、求解器和依赖版本。
4. **同口径**：总耗时是否包含加载、导出和子进程必须一致；外部工具包含其子进程资源。
5. **重复与报告**：性能点至少重复 3 次，报告中位数和离散程度；确定性正确性回归不必机械重复。
6. **保留异常**：timeout、OOM 和 error 原样进入结果表，不能删除“不好看”的数据点。

若无法满足某项约束，报告必须显著标注，结论降级为观察性结果，而非严格对比。

## 5. 扩展性实验

每次只改变一个主要维度，先固定其他参数：

- 历史长度：事务数或操作数。
- 并发形状：会话数。
- 事务宽度：每事务操作数。
- 冲突密度：键空间、读写比例或分布。
- 写值假设：唯一写值与重复写值，仅在兼容 checker 间比较。

扫描点由研究问题和预实验决定，不默认执行巨大笛卡尔积。横轴使用实际规模，图注注明参数、重复次数、预算和协议版本。

## 6. 采集边界

- 现有 `Profiler`、runtime CSV 和阶段记录继续作为原始数据来源，统一分析层负责转换。
- 外部 checker 的子进程 PID 必须纳入监控；无法完整采集时明确缺失。
- Logger、序列化和图表生成开销与 checker 求解开销分开报告。
- 不在每个用例后依赖强制 GC 制造“公平”；如保留现有行为，应对所有参评实现一致并记录。

## 7. 验收

- 每个性能数字都能回链到 run、历史哈希、环境和原始记录。
- 分析脚本能校验阶段与总耗时关系、缺失值和非结论状态。
- 同一 artifact 重复聚合得到相同表格与图数据。
- 报告完整披露比较协议及未满足项，不包含无法由原始数据重建的结论。
